# 退款与售后工单说明（阶段 4）

本阶段把“退款”和“售后咨询”拆成两条流程。退款会改变订单状态和库存，属于强事务业务；工单负责记录问题、回复和处理轨迹，不直接修改订单或库存。

## 1. 模块职责

```text
smartmall-business
  refund/  退款状态机、审核事务、Repository 接口
  ticket/  工单状态机、回复与处理记录、Repository 接口

smartmall-infrastructure
  refund/  refund_request 的 MyBatis 实现
  ticket/  after_sales_ticket、ticket_message 的 MyBatis 实现

smartmall-web
  refund/  HTTP 接口、请求校验、管理员审核权限
  ticket/  HTTP 接口、请求校验、当前登录人转换

smartmall-application
  V4__create_refund_and_ticket_tables.sql
```

业务模块不知道 JWT、Controller 或 MyBatis。Web 层从 `AppUserPrincipal` 取得当前登录人的 ID 和用户名，再放进 Command 传给业务层；这样审计字段可信，不能由浏览器伪造。

## 2. 全额退款流程

只有 `PAID` 订单可以提交退款，并且本阶段只做整单全额退款：

```text
PAID --提交申请--> REFUNDING --管理员通过--> REFUNDED
                         \--管理员驳回--> PAID
```

接口：

```text
GET  /api/refunds
GET  /api/refunds/{id}
POST /api/orders/{orderId}/refunds
POST /api/refunds/{id}/approve   ADMIN
POST /api/refunds/{id}/reject    ADMIN
```

提交申请时，`RefundService.create()` 先执行条件更新：

```sql
UPDATE orders SET status = 'REFUNDING'
WHERE id = ? AND status = 'PAID';
```

受影响行数必须为 1。两个请求同时提交时，只有第一个能改变状态；第二个不会再创建有效申请。数据库还用部分唯一索引限制每个订单只有一笔 `PENDING_REVIEW` 退款。

管理员通过时，下面三步处于同一个 `@Transactional` 事务：

1. 订单由 `REFUNDING` 条件更新为 `REFUNDED`。
2. 退款单由 `PENDING_REVIEW` 条件更新为 `COMPLETED`，写入审核人和时间。
3. 遍历原订单明细，把每件商品库存加回去。

任何一步抛出异常都会整体回滚，因此不会出现“退款单成功但库存没恢复”的半完成状态。重复审核也会因条件更新失败而终止，避免库存重复增加。驳回只把订单恢复为 `PAID`，不会恢复库存。

## 3. 售后工单流程

工单必须关联一个已存在订单，创建时保存订单号、客户 ID 和客户名称快照。状态只能按顺序向前推进：

```text
OPEN -> PROCESSING -> RESOLVED -> CLOSED
```

不能跳级、回退，也不能在 `CLOSED` 后继续回复。接口：

```text
GET   /api/tickets
GET   /api/tickets/{id}
POST  /api/tickets
POST  /api/tickets/{id}/messages
PATCH /api/tickets/{id}/status
```

`after_sales_ticket` 保存工单当前状态；`ticket_message` 保存两类时间线记录：

- `REPLY`：沟通或处理回复，保存发送人和正文。
- `STATUS_CHANGE`：状态变化，保存旧状态、新状态、操作人和可选说明。

状态更新 SQL 同样带旧状态条件。成功后业务层插入一条 `STATUS_CHANGE`，两项操作在同一事务中，因此详情页时间线能解释每次状态为何变化。

## 4. 前端调用链

```text
RefundsView / TicketsView
  -> refunds.ts / tickets.ts
  -> Axios 统一实例自动加入 Bearer Token
  -> Vite 将 /api 转发到 Spring Boot
  -> Controller 做参数和权限校验
  -> Service 执行业务状态机
  -> Repository 接口
  -> MyBatis Repository + Mapper
  -> PostgreSQL
```

订单页上的“申请退款”只在 `PAID` 状态出现。退款审核按钮只对前端已知的 `ADMIN` 显示，但真正的安全边界是后端 Controller 上的 `@PreAuthorize("hasRole('ADMIN')")`；普通用户即使手工构造请求也会收到 403。

## 5. 数据库迁移注意事项

不要修改已在数据库执行过的 `V1`、`V2`、`V3`。应用下次以 `local` Profile 启动时，Flyway 会自动执行 `V4`：扩展订单状态约束、增加 `refunded_at`，并创建退款、工单和工单消息表。若迁移失败，应先看启动日志中的第一条 PostgreSQL/Flyway 错误，不要删除 `flyway_schema_history` 或直接改旧迁移校验值。
