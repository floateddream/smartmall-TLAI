# 知识库文档处理说明

## 1. 功能边界

后台用户上传文件后，原文件写入 MinIO，文档元数据写入 PostgreSQL。后台定时任务随后自动解析正文、分段、调用活动的 Embedding 模型，并把 1024 维向量写入 pgvector。

```text
KnowledgeView
  -> POST /api/knowledge/documents (JWT + multipart)
  -> KnowledgeDocumentService
  -> ObjectStorage 端口
  -> MinioObjectStorage
  -> smartmall-documents 桶

KnowledgeDocumentService
  -> KnowledgeDocumentRepository 端口
  -> MybatisKnowledgeDocumentRepository
  -> knowledge_document 表（UPLOADED）

KnowledgeDocumentProcessingJob
  -> 领取一份 UPLOADED 文档（PROCESSING）
  -> Apache Tika 提取正文
  -> KnowledgeTextSplitter 分段
  -> AiEmbeddingService 调用活动 Embedding 模型
  -> knowledge_chunk 保存正文片段和 vector(1024)
  -> READY；异常时 FAILED 并保存失败原因
```

系统已经在这份向量索引之上增加问题向量化、pgvector 余弦相似度检索和引用式 RAG 回答。

## 2. 模块职责

```text
smartmall-knowledge
  model/       文档、片段和处理状态领域对象
  application/ 上传、查询、重试、解析分段和索引编排
  processing/  文本解析和 Embedding 端口
  repository/  文档及片段持久化端口
  storage/     原始文件对象存储端口

smartmall-ai
  application/AiEmbeddingService  读取活动模型并生成向量

smartmall-rag
  组合相似片段、系统上下文和对话模型回答

smartmall-infrastructure
  document/              Apache Tika 文本解析适配器
  ai/                    knowledge 与 AI 模块的适配器
  persistence/knowledge/ MyBatis 文档、片段和 pgvector 实现
  storage/minio/           MinIO SDK 适配器和配置

smartmall-job
  每 3 秒尝试领取一份待处理文档；一次只处理一份

smartmall-web
  knowledge/  知识库 HTTP 接口和响应 DTO

smartmall-application
  V9__create_knowledge_base.sql 和运行参数
```

浏览器不会直接连接 MinIO，也拿不到 Access Key。上传和下载都经过 Spring Boot，并继续使用现有 JWT 与 RBAC。

## 3. 本地配置

在被 Git 忽略的文件中维护真实凭据：

```text
backend/smartmall-application/src/main/resources/application-local.yml
```

把下面内容合并进已有的 `smartmall:` 节点，不要重复创建顶层 `smartmall:`：

```yaml
smartmall:
  storage:
    minio:
      endpoint: http://<服务器IP>:9000
      access-key: 你的应用AccessKey
      secret-key: 你的应用SecretKey
      bucket: smartmall-documents
  knowledge:
    processing:
      initial-delay: 5000
      poll-interval: 3000
  rag:
    top-k: 5
    min-score: 0.35
    max-context-characters: 10000
```

部署环境也可以使用环境变量：

```text
SMARTMALL_MINIO_ENDPOINT
SMARTMALL_MINIO_ACCESS_KEY
SMARTMALL_MINIO_SECRET_KEY
SMARTMALL_MINIO_BUCKET
SMARTMALL_RAG_TOP_K
SMARTMALL_RAG_MIN_SCORE
SMARTMALL_RAG_MAX_CONTEXT_CHARACTERS
```

应用凭据应只拥有 `smartmall-documents` 的读写权限，不要填写 MinIO Root 凭据。

还必须在“AI 模型”页面测试并启用 Embedding 模型：

| 字段 | 推荐值 |
|---|---|
| 模型类型 | `EMBEDDING` |
| 供应商 | `Ollama` |
| 接口地址 | `http://<服务器IP>:11434/v1` |
| 模型名称 | `bge-m3` |
| 向量维度 | `1024` |

## 4. 处理规则

- 状态流转：`UPLOADED -> PROCESSING -> READY`，异常时进入 `FAILED`。
- 任务启动 5 秒后开始轮询，默认每 3 秒领取一份文档。
- 领取使用 PostgreSQL `FOR UPDATE SKIP LOCKED`，避免多个实例重复处理同一文档。
- 分段最大 1200 个字符，相邻片段重叠 120 个字符，优先在自然标点处断开。
- 单份文档最多提取 200000 个字符，超过后提示拆分文档。
- 分段与状态更新在同一个事务中完成，避免留下半份索引。
- 处理失败会在页面显示原因；管理员可以点击重试按钮重新入队。
- 已上传但仍处于 `UPLOADED` 的历史文档，会在新版后端重启后自动处理。

为适配 2 核 4 GB 服务器，当前每次只处理一份文档，Embedding 片段也按顺序调用。处理较大的 PDF 时处于 `PROCESSING` 数分钟属于正常情况。

RAG 查询默认返回最相似的 5 个片段，只保留相似度不低于 `0.35` 的结果。没有片段达到阈值时，不调用对话模型，直接提示知识库依据不足。

## 5. 数据位置

| 数据 | 保存位置 | 说明 |
|---|---|---|
| PDF、DOCX、TXT、Markdown 原文件 | MinIO `smartmall-documents` | 对象键由后端生成，不使用用户传入路径 |
| 文件名、大小、类型、状态、上传人 | PostgreSQL `knowledge_document` | 用于页面列表和处理状态 |
| 文本片段和 1024 维向量 | PostgreSQL `knowledge_chunk` | 使用 pgvector HNSW 索引 |

删除文档时，后端先删除 MinIO 原文件，再删除 PostgreSQL 元数据；`knowledge_chunk` 通过外键级联删除。

## 6. 文件限制

- 支持：`.pdf`、`.docx`、`.txt`、`.md`
- 单文件最大：20 MB
- 页面每批最多选择 20 个文件，以 3 路并发逐个调用单文件上传接口
- 每个文件独立显示上传进度；部分失败不会影响其他文件，并可只重试失败项
- 空文件拒绝上传
- 原始文件名最长：255 个字符
- MinIO 对象键采用 `documents/yyyy/MM/UUID.ext`，避免路径穿越和同名覆盖

- Apache Tika 负责识别并提取实际文件内容；损坏或伪造格式会进入 `FAILED`
- 提取后的正文最多 200000 个字符

## 7. 接口与权限

| 方法 | 地址 | 权限 | 用途 |
|---|---|---|---|
| `GET` | `/api/knowledge/documents` | `knowledge:view` | 分页查询文档 |
| `POST` | `/api/knowledge/documents` | `knowledge:manage` | 上传文档 |
| `POST` | `/api/knowledge/documents/{id}/retry` | `knowledge:manage` | 重试处理失败的文档 |
| `GET` | `/api/knowledge/documents/{id}/download` | `knowledge:view` | 下载原文件 |
| `DELETE` | `/api/knowledge/documents/{id}` | `knowledge:manage` | 删除原文件和元数据 |

V9 将两个权限都授予内置 `ADMIN` 和 `OPERATOR`。后续可以在“用户与权限”页面调整自定义角色。

## 8. 测试步骤

1. 在 AI 模型页面测试并激活 `bge-m3` Embedding 配置。
2. 配置 `application-local.yml`，使用 `local` Profile 重启后端。
3. Flyway 日志确认数据库迁移到 V9，启动前端并进入 `/knowledge`。
4. 上传 TXT、Markdown、DOCX 或 PDF，页面应从“已上传”变为“处理中”。
5. 处理完成后，页面应显示“可检索”和片段数量。
6. 后端控制台应出现“知识库文档处理开始”和“知识库文档处理成功”日志。
7. 若状态变为“处理失败”，查看页面原因和后端日志，修正后点击重试按钮。
8. 在 MinIO 控制台确认原文件存在，并用以下只读 SQL 检查索引结果：

```sql
SELECT id, original_name, status, chunk_count, error_message
FROM knowledge_document
ORDER BY id DESC;

SELECT document_id, COUNT(*) AS chunks
FROM knowledge_chunk
GROUP BY document_id
ORDER BY document_id DESC;
```

9. 进入 AI 助手，开启“知识库增强”，使用文档中能明确回答的问题进行测试。
10. 回答下方应显示引用来源、片段编号和相似度；关闭开关后仍可进行普通对话。

删除属于不可恢复操作，页面会在执行前二次确认。
