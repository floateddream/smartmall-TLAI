# 受控 Agent 写操作说明

## 1. 当前范围

业务 Agent 新增两个需要二次确认的写操作：

| 操作 | 用途 | 所需权限 |
|---|---|---|
| `createAfterSalesTicket` | 基于现有订单创建售后工单 | `ticket:create` |
| `addTicketReply` | 向未关闭的工单追加回复 | `ticket:reply` |

支付、订单取消、退款审核、删除数据和 RBAC 权限调整仍然禁止由 Agent 执行。

## 2. 为什么不会直接写入

```text
用户描述需求
  -> 模型只生成严格 JSON 操作计划
  -> Java 校验操作白名单、参数和当前用户权限
  -> 服务端生成随机确认令牌
  -> PostgreSQL 只保存令牌的 SHA-256 哈希和规范化参数
  -> 前端展示待确认卡片
  -> 用户点击“确认执行”
  -> 服务端校验令牌归属、有效期和最新权限
  -> 数据库原子抢占执行权
  -> 调用现有 TicketService
  -> 保存执行结果并写入 agent_tool_audit
```

模型不能提供执行者 ID、用户名、确认令牌或权限。执行者身份始终来自当前 JWT 登录用户。

## 3. 防重复与有效期

- 确认令牌使用安全随机数生成，有效期为 10 分钟。
- 原始令牌只返回前端一次，`agent_action_confirmation` 表仅保存哈希。
- 确认记录与创建它的用户绑定，其他账号使用同一令牌会得到“待确认操作不存在”。
- 确认时会重新检查权限，因此计划生成后被移除权限也无法执行。
- 状态通过 `PENDING -> EXECUTING -> SUCCEEDED` 推进；并发点击只有一个请求能抢占成功。
- 已成功令牌再次提交只返回已有结果，不会重复创建工单或重复回复。
- 点击取消后状态变为 `CANCELLED`，不会调用业务写入服务。

## 4. 数据库与接口

Flyway `V13__create_agent_action_confirmation.sql` 创建确认记录表。后端重启后 Flyway 会自动执行该迁移。

```http
POST /api/ai/agent/confirm
Content-Type: application/json

{"token":"页面返回的确认令牌"}
```

```http
POST /api/ai/agent/cancel
Content-Type: application/json

{"token":"页面返回的确认令牌"}
```

这两个接口都要求登录账号拥有 `ai:chat`，确认接口还会按具体操作重新校验 `ticket:create` 或 `ticket:reply`。

## 5. 页面测试

1. 重启后端，让 Flyway 执行 `V13`，然后刷新前端。
2. 使用同时拥有 `ai:chat` 和相应工单权限的账号登录。
3. 在“AI 助手”打开“业务 Agent”。
4. 输入“给订单号 SM20260924082608B125E3 创建一个物流问题工单，普通优先级，主题是物流停滞，描述是三天没有更新”。订单号会在服务端精确解析为内部订单 ID。
5. 核对橙色确认卡片，点击“确认执行”，成功后会显示绿色结果。
6. 再尝试“给工单 ID 3 回复：我们已经联系仓库核实”，核对后确认。
7. 可在工单页面和数据库中核对结果，也可以点击“取消”验证没有写入。

如果订单或工单不存在、工单已关闭、令牌过期或权限不足，后端会返回明确业务错误，写操作不会成功。
